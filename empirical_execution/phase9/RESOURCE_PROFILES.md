# Canonical resource profiles and observed policy qualification

`resource_profiles.py` extends the frozen Phase 8 native-C selector to canonical
registered task scopes. It changes no Phase 3–8 source, tolerance, failure rule,
or default. No native observation has been accepted and no primary experiment
has started.

The result is a prospective operational count policy supported by matching
accepted development observations. It is not a runtime bound, memory bound,
optimizer qualification, historical-authenticity proof, or primary-study permit.
A default cap refusal remains a refusal until the appropriate actual observations
and review exist. Unknown graph-dependent coefficient demand remains unknown.

## Supported scope

The compiler rebuilds the frozen 43-group, 21,332-job registry. A bound
`phase9_scope` selects complete canonical groups and complete extension recipes
owned by one immutable family root. Its fields are `key`, `group_ids`, and
`extension_recipes`; selected groups must be among `_dossier_group_ids`.
There is no caller-authored profile list or job-level cherry-picking.
Every covered job is represented, including empty or unavailable request arms.

| Route | What must match | What is qualified |
| --- | --- | --- |
| Ridge workers | Both encoder IDs/revisions, resolved dimensions, seeded projection, calibration choices, deletion unit and complete actually executed distinct-unit schedule, method, precision, decoder, process panel, persistence, common resource limits, and full source dependencies | Observed worker configuration and count extent; the required FP64 audit observations also bind their auxiliary worker/configuration and full checkpoints |
| Mixed encoders and projections | Exact cache rows from the accepted original development population; fixed registered projection reproduced in FP64, then the same stored FP32 result | The actual transformed inputs, never retagged native observations |
| Larger structural panels | Actual resolved panel size and graph-only configuration, real disjoint pilot inputs, matching arm, horizon/checkpoints, and fresh-graph setting | The measured frozen structural route; hypothetical output-width forecasts are not task labels |
| Convex F branch | Actual selected-row counts at initial state and every canonical release; joint dimension/output/backend/settings match; dense observed selected inputs | Individual exact verifier calls and their observed count extent; no trajectory, optimization, warm-start, or fitting-time claim |
| Initial utility reference | The same pointwise convex requirements and the utility branch's separate budget lock | Its actual executed cap, never a substituted global cap |

FP32 workers do not inherit the unimplemented FP64 audit hook. FP64 B-E and
P-I/P-S/P-R require light membership/moment audits where the scheduler invokes
them; all eight methods require full audits on the registered flagged paths.
Only full summary audits consume the fresh symbolic coefficient guard.
P-R rank-basis storage does not substitute for that complete coefficient count.

Full-refit, ANN, negative controls, graph-envelope diagnostics and other branches
outside these added audit/verifier guards are explicitly marked
`outside_added_audit_and_verifier_caps`. Their common base lock and their own
frozen acceptance, numerical and resource gates still apply. This selector
makes no additional feasibility claim for them. Global human and statistical
owners use their separate frozen gates and are not retagged as task-family
resource observations.

## Source and execution lineage

The qualifier first executes actual source/cache acceptance and the unchanged
`phase6.dispatch.development_acceptance`. That gate checks original prepared
records, disjoint record/source populations, original labels, accepted semantic
cache rows, actual baseline service reports, the resource derivation and the
precision dossier. Unlabeled target corpora still need the separate accepted
labeled baseline resource dossier required by that frozen gate. This requirement
does not create labels for their graph-only target arrays.

For each profile, `replay_derived_package` reconstructs the pilot's curator and
learner arrays from those accepted caches. It separately binds mixed encoders,
projection seed/matrix/output, priority, threshold, retained graph, targets and
all package files. Accepted original source/cache paths keep their existing
literal absolute or relative semantics. Observation packages and observation
artifacts must remain inside the immutable owner root.

Worker observations bind the complete frozen Python dependency map, actual
prospective configuration, raw inputs, request hash, construction and repair
process records. Audit observations also bind the auxiliary every-release
service, its exact configuration, policy, requests, snapshot/head checks, and
complete coefficient comparisons where required. Numeric tolerances cannot be
weakened. Actual CPU time, wall time and the reported RSS indicators must fit the
unchanged common limits. Configuring a horizon without executing its complete
distinct-unit checkpoint schedule is insufficient.

Graph and convex observations must come with the executable
`resource_measurement.py` producer's retained request, configuration, invocation,
Python executable hash, process record, source map and complete output hashes.
The receiver checks these records against each other and current code, replays
graph memberships or the exact certificate, and rejects software-only roles,
changed artifacts and failed processes. See `RESOURCE_MEASUREMENT.md` for the
collector. A schema label or ad hoc timing number is not sufficient intake.
These byte checks still require later accountable external review of historical
execution, source authenticity and hardware/runtime conditions.

## Counts and limits

For original panel size N and curator dimension c, the frozen audit predicate
cap checks `N*(N-1)/2*c`. This is an original-shape count proxy, not an exact count
of executed instructions: tiled scoring and repeated retained-graph scans add
work. For learner dimension d and q outputs, a complete symbolic key contains
`d*(d+1)/2 + d*q + 1` packed coordinates. The future number M of fresh designated
keys is graph-dependent. The selector does not replace it with observed rank,
selected-row count, or an invented empirical constant.

The common pair cap covers actual resolved shapes. The common coefficient cap
is the minimum, over full-summary profile classes, of the maximum jointly
observed complete coefficient demand within each matching class. It cannot be
smaller than the unchanged default. A future M above that cap preserves the
original audit failure. This setting does not prove every future checkpoint
fits. Low coordinate count is not a constant-memory or total-byte claim.

For convex verification the actual guard is `selected_rows*d*q`. The compiler
records counts separately for every canonical job, then takes the actual
maximum, rather than retaining only the first trajectory. A single qualifying
pointwise observation must jointly cover the selected count, dimensions,
outputs and verifier settings. Nonempty observations must have feature density
at least 0.95; empty targets are explicit zero-work cases. Seven Civil outputs
cannot qualify twenty Stack outputs. A small sparse lexical report cannot
qualify dense semantic verification.

The utility executor ignores the global convex cap. Without its own lock, its
unchanged limit is 2,000,000. Above that demand the qualifier refuses unless
`convex_verification_development` exactly projects the accepted producer
observations and common development lock, and the frozen
`recipes.select_verification_budget` reproduces its saved budget. That selector's
four-times-rate and memory formula remains explicitly a forecast. The new
joint observed count requirement does not turn that forecast into a bound.

No cost extrapolation is used to invent native throughput or RSS. Equal or
larger N, d, q and observed coefficient count do not bound graph density, source
overlap, symbolic incidence/fan-in, dictionary operations, serialization,
allocator behavior, decoder iterations or conditioning. Wait4 RSS and sampled
process-tree RSS are descriptive indicators; address-space limits are a
different quantity. Auditor lifetime RSS plus sampled worker RSS is not a
simultaneous-peak certificate. Producer process time excludes parent intake and
copying; its report states that scope separately.

Qualification itself has costs. It resolves and replays groups, rebuilds
transformed graphs, gathers cache rows, reads/hashes artifacts and rechecks
certificates. These steps may repeat by group/profile and allocate dense arrays.
They are not free preflight or repair timing. No native end-to-end qualification
peak memory or throughput has been measured.

## Prospective workflow and interfaces

1. Prepare original archives, accepted caches, calibration, guarded task inputs,
   a genuinely disjoint baseline development dossier, and supplied preliminary
   testimony binding its exact development source replay. Insert immutable
   `phase9_scope` and `phase9_stable_root` before resource selection with the
   scheduler's `prepare-resource` stage.
2. Call `compile_profiles(owner_key, bundle, base_dir=original_root)` with its
   default `require_acceptance=True`. It returns the complete profile manifest
   and internal replay context. Freeze a plan with role
   `actual_disjoint_development`, its exact `profile_manifest_sha256`, ordered
   complete `observation_ids`, and `development_resource_lock_sha256`.
   `require_acceptance=False` exists only for software inspection and cannot
   produce a policy or pass the public verifier.
3. Collect actual worker/audit or graph/convex observations under the matching
   profile settings. Retain planned failures and all output bytes. Do not use
   this step to replace unavailable actual inputs with metadata or lexical
   fixtures. The producer command is documented separately.
4. Build a qualification request with exactly `owner_key`, a bound `bundle`,
   and `evidence`. The bundle file descriptor is `{path, sha256, kind: "json"}`
   (the same frozen format used by staged dossiers). Evidence contains a
   `{path, sha256}` plan descriptor and the
   ordered observation entries. Each entry supplies `observation_id`,
   `profile_id`, `input_package`, and its relevant artifact descriptors.
5. Run the read-only qualification command below. It exports an execution policy
   only if all requested profile observations and unchanged acceptance checks
   pass. It never executes a benchmark or fits a model.
6. Supply the receipt/evidence to the Phase 9 `prepare-review` stage. That stage
   attaches them inside the candidate, produces a review request, and waits for
   supplied complete review. `finalize-review` and the scheduler reverify the
   receipt plus every unchanged primary gate. A receipt alone never unlocks
   primary execution.

```bash
python empirical_execution/phase9/resource_profiles.py \
  --request /absolute/stable/dossier/resource_request.json \
  --out /absolute/stable/dossier/new_resource_qualification
```

The programmatic APIs are:

```python
manifest, context = compile_profiles(owner_key, bundle, base_dir=root)
receipt = qualify_owner_resources(owner_key, bundle, evidence, base_dir=root)
verified = verify_owner_resources(receipt, owner_key, bundle, evidence, base_dir=root)
```

Verification recomputes the complete receipt and raises on a blocked or changed
result. Qualified receipts expose `execution_policy` and exact `covered_job_ids`.
The scheduler requires coverage for every selected canonical job and preserves
each owner's policy and literal root; it does not relocate signed inputs.

The input fingerprint excludes derived `execution_policy`,
`resource_policy_qualification` and `resource_policy_observations`, and final
review testimony, while retaining the immutable development replay digest,
`phase9_scope`, stable root and all underlying inputs. Profile signatures bind
backend/tolerances separately, and the selected policy has its own receipt
binding. Thus attaching the receipt or replacing preliminary testimony with a
complete review does not create a hash cycle. Changing development identity,
job scope, source/cache configuration or actual observations changes the receipt.
The final external review includes the attached qualification and evidence.

## Software evidence and missing evidence

`check_resource_profiles.py` uses tiny numerical algebra and invented metadata
solely to test contracts. Positive qualifier controls mock upstream source,
calibration and development acceptance. Worker process numbers in those controls
are not measurements. Producer-receiver controls deliberately construct
untrusted metadata to test consistency; real producer subprocess checks are
reported separately. The same toy bundle fails unmocked actual acceptance.
No synthetic empirical dataset, semantic cache, human response, native timing,
or paper-ready result was created.

The focused checker covers canonical scope agreement, cache/projection replay,
identity and process distinctions, count boundaries, unavailable arms, utility
cap separation, source-bound receipt consistency, changed-input refusal and
attachment/final-testimony stability. Provisional reports and their exact
source copies are retained under `results/resource_checks_attempt*` and
`history/resource_attempt*`. Final result paths and exact hashes are recorded
in `results/resource_release_manifest.json`.

Authentic archives, model/cache files, genuine calibration/human evidence and
matching source-disjoint native observations remain unavailable. This module
implements the broader intake and count-setting adapters; it does not complete
native feasibility, convex optimization measurements, end-to-end preparation
memory qualification, branch-specific full-refit/ANN acceptance, or the primary
study. Those remain evidence/execution obligations, not hidden successes.

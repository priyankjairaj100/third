Ranked findings

F1. Medium severity / confirmed source-description defect: the empirical service does not reject retries as the manuscript says.

Location: manuscript/third_working_draft.tex:208-211.
Affected claim: the frozen empirical P-I interface rejects repeated and already-deleted identifiers before mutation, while only the earlier reference treats retries as no-ops.

Evidence: empirical_execution/ccu/summary.py:336-352 does implement the strict low-level integer-ID kernel. However, the public empirical wrapper, empirical_execution/phase5/methods.py:97-105, first computes fresh = sorted({lookup[i] for i in ids} & alive), then passes that filtered list to the strict kernel. Duplicate input IDs have already been collapsed and already-deleted IDs discarded. phase6/methods.py:96-105, 233-255 and 276-288 forward ordinary P-I to that wrapper. The worker uses this service path. The frozen phase6/check_state_audit_semantics.py:82-84 and 190-194 explicitly exercise duplicates and expect an exhausted retry to have zero fresh deletions.

Concrete counterexample by direct code evaluation: with a live ID u and available budget, wrapper.delete([u,u]) passes [lookup[u]] to the kernel and consumes one deletion. Calling wrapper.delete([u]) again passes [] and consumes none, including after exhaustion. Neither call is rejected for duplication/repetition. Unknown IDs are still rejected; fresh over-budget requests are still rejected. This is a policy mismatch in the prose, not evidence of wrong fresh-deletion statistics.

The previous author assertion in manuscript/claims_review_20261016.json:168-172 inspected only the low-level kernel. manuscript/build_review.py:126-129 checks for exception text in that file and therefore cannot establish the wrapper's public behavior. I did not accept that assertion as proof.

Smallest defensible correction: name all relevant layers. State that IndexedRidgeSummary.delete is strict, while the frozen Phase 5/6 empirical SummaryService normalizes repeated/already-deleted IDs to fresh deletions; the earlier mathematical reference also treats retries as no-ops. Do not rewrite frozen code or historical results to match the incorrect sentence. A later evidence/checker version should trace the wrapper as well as the kernel and preserve the old review as historical.

F2. Medium severity / missing implementation-cost qualification: the stated update bound is valid for the abstract indexed algorithm, but does not cover the shipped API overhead.

Locations: manuscript/third_working_draft.tex:204-229 and 770-777, especially the O(Q) input-handling statement at 776-777.
Affected claim: presenting O(Q + Phi0 + s M0) as the sequence-wide update cost of the empirical P-I implementation without identifying its additional request costs.

Evidence: the stable-handle mutation logic in empirical_execution/ccu/summary.py:299-334 supports the incidence/potential/vector-merge argument. But its public delete method sorts the entire validated request at line 350. The empirical string-ID wrapper rebuilds lookup for all public IDs on every call at empirical_execution/phase5/methods.py:100, then sorts fresh indices at line 103. These operations happen even when the coefficient map has no incident key. The exact mathematical reference algorithm_round2.py:157-175 does not sort requests, so this finding does not refute the abstract bound.

Counterexample: use N identical feature/label rows with a complete ordered similarity graph and K<N. Their identical record statistic t gives the telescoping polynomial t(1 - x_all). Truncation leaves only the constant coefficient: M0=1, L0=Phi0=0, with fixed statistic dimension. A single fresh singleton request has Q=1 and no coefficient touches, but the empirical wrapper still reconstructs an N-entry lookup. Its update cannot be O(1+s) uniformly in N. For direct low-level calls, a sufficiently disordered batch of q fresh IDs can additionally require comparison-sort work of order q log q despite the same constant coefficient map.

Let B be the number of API calls, N the fixed public unit-ID count, q_b the supplied IDs in call b, f_b the fresh unique IDs forwarded by the wrapper, and Q=sum_b q_b. Under unit-cost word-sized identifiers and expected constant-time dictionary/set operations, a safe shipped-wrapper bound is

  O(B(N+1) + sum_b [q_b + f_b log(f_b+1)] + Phi0 + s M0).

For direct low-level calls on arbitrary unsorted request lists, a safe bound is

  O(B + Q + sum_b q_b log(q_b+1) + Phi0 + s M0).

The kernel receives an already sorted list from the wrapper; do not double-charge a second arbitrary-order sort. String decoding, first-time hashing, comparison, and arbitrary-precision identifier costs require additional byte/bit accounting. The B term covers empty requests, which are legal; it can be absorbed into Q only when calls are nonempty. The wrapper also allocates a temporary O(N) lookup, plus request containers, relevant to peak workspace.

Smallest defensible correction: explicitly assign Equation (7)'s core bound to the abstract/reference indexed update under its input model, and separately disclose the frozen API's lookup and sorting costs (and the nonempty-call convention or B term). Preserve the current frozen implementation and include these operations in future complete-cost timings. Construction, solving, serialization and exact-arithmetic bit costs should remain separate as already stated.
